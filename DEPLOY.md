# Deploying ProfileForge to the shared host (rametric.com)

Target: CloudLinux + LiteSpeed + Passenger on the same cPanel account that hosts
rametric.com, mounted at **https://www.rametric.com/profile-forge/**. The pattern
is the one `prompt-forge` already uses: code lives in `~/profile-forge` (outside
the docroot), Passenger mounts it under a subdirectory URI.

Build machine assumption: linux x86-64 with Node 20 (same major as the host's
Node selector) — native modules (`@node-rs/argon2`) and Prisma 7 driver-adapter
client are shipped prebuilt, nothing is installed on the server.

## Layout on the server

```
~/profile-forge/                 # PassengerAppRoot — the built app (uploaded)
  server.js                      # Next standalone server (startup file)
  .next/static/                  # client assets (copied in after build)
  public/                        # static public assets
  prisma/ + node_modules/prisma  # only if server-side migrate is ever needed
  uploads/                       # UPLOADS_DIR — user CVs & artifacts (runtime)
~/public_html/profile-forge/.htaccess   # Passenger mount (created by cPanel)
```

Environment variables (set in cPanel → Setup Node.js App → env vars):

| Variable | Value | Notes |
|---|---|---|
| `DATABASE_URL` | `postgresql://<pguser>:<pgpass>@localhost:5432/<pgdb>` | from cPanel → PostgreSQL Databases |
| `NEXT_BASE_PATH` | `/profile-forge` | **baked at build time** — must match the mount URI |
| `APP_SECRET` | any random hex ≥ 32 chars | pin it: sessions + encrypted per-user keys break if regenerated |
| `UPLOADS_DIR` | `/home/ramemvpl/profile-forge/uploads` | absolute, outside docroot |
| `NODE_ENV` | `production` | |
| `OPENROUTER_API_KEY` | leave **unset** on a public demo | per-user keys entered in Settings take priority anyway (R6: env → user row) |

## One-time cPanel steps (UI only — no shell needed)

1. **PostgreSQL**: cPanel → PostgreSQL Databases → create DB + user, grant all.
   Note the generated names (`ramemvpl_*`).
2. **Node app**: cPanel → Setup Node.js App → Create:
   Node 20 · app root `profile-forge` · app URL `profile-forge` · startup file
   `bootstrap.js` (runs migrations, then boots the server). Then add the env
   vars above — no npm install needed, `node_modules` ships prebuilt.
3. **Remote DB access** (optional): cPanel → Remote PostgreSQL → add the build
   machine's IP. **On this host the page is disabled** — apply migrations via
   phpPgAdmin instead (see "Migrations & demo seed").
4. Nothing else — `.htaccess` mount is generated by step 2.

## Build (build machine)

```bash
git worktree add ../pf-deploy HEAD       # clean tree, never the dirty workdir
cd ../pf-deploy && npm ci                # postinstall runs prisma generate
NEXT_BASE_PATH=/profile-forge npm run build
cd .next/standalone
cp -r ../../public . && cp -r ../../.next/static .next/static
cp -r ../../prisma .                     # schema + migrations for bootstrap
mkdir -p node_modules/@prisma
cp -r ../../node_modules/prisma node_modules/
cp -r ../../node_modules/@prisma/engines node_modules/@prisma/
# add bundle-only files: bootstrap.js (Passenger startup: migrate deploy then
# require ./server.js) and prisma.config.js (env-driven, no dotenv)
tar czf ../../profileforge-bundle.tar.gz .
```

Upload the single `.tar.gz` (SFTP), then cPanel File Manager → `~/profile-forge`
→ Extract. Migrations apply automatically on the first Passenger start (and on
every restart — `migrate deploy` is idempotent), so no manual SQL, no phpPgAdmin.

## Migrations & demo seed

**Automatic.** The bundle ships the Prisma CLI + engines + `prisma/migrations`;
the Passenger startup file (`bootstrap.js`) runs `prisma migrate deploy` before
booting the server. Future schema changes = commit migrations, rebuild bundle,
re-extract, restart. (phpPgAdmin's SQL tab on this host cannot execute
multi-statement batches — do not paste SQL there.)

## Verify

- `GET https://www.rametric.com/profile-forge/` → login page, styles load
  (assets are served under `/profile-forge/_next/…` because of the baked basePath).
- Register/demo-login → generate flow with a key entered in Settings.

## Redeploy

Rebuild the bundle the same way and Extract over `~/profile-forge` (keeps
`uploads/` and `.appsecret` if present), then cPanel → Restart. `uploads/` and
`.appsecret` are runtime files — never delete them on redeploy.

## Security notes

- `DATABASE_URL`, `APP_SECRET` live in the cPanel app's env config — never in
  the repo, never in `.htaccess` (unlike an older prompt-forge `.htaccess` that
  carries a `SetEnv ZAI_API_KEY`; rotate that key and move it to the Node app
  env config when convenient).
- A public demo is multi-user with per-user keys; the env-level OpenRouter key
  should stay unset so no shared key is exposed to strangers.
